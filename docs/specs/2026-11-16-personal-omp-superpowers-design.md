# Личный omp-superpowers: дизайн

Статус: согласован пользователем через форму decision=approve; разрешены создание и push форка, реализация, отдельные проверки и переключение omp. Установка ещё не изменена.

## Цель и причина

Использовать в omp закреплённую личную версию готовой адаптации Superpowers, не переписывая существующий omp-слой. Убрать зависимость совместимости Ponytail/SDD от случайной загрузки глобальной памяти. Сохранить самостоятельный receiving-code-review из @omp-utils/code-review.

Пользователь согласовал процесс исходного форка: промежуточное ревью по риску, независимые задачи в параллельных worktrees, максимум три раунда исправлений. Пользователь переходит на omp; плагин Superpowers в Codex уже удалён и повторно не устанавливается.

## Исходное состояние и источник

- Основа: LoneExile/omp-superpowers, версия 7.0.2-omp.3, commit fad5b9e7ec578fbac11c7dbe1b251ceb1d7f19a9. Не собирать из плавающего main.
- Цель: личный GitHub-форк YarikMix/omp-superpowers; такого репозитория при проверке нет. При ограничении GitHub на второй форк одного network не обходить его копированием несвязанной истории: проверить уже существующий личный форк и сохранить происхождение.
- Рабочая копия: ~/projects/omp-superpowers, сейчас отсутствует.
- Официальный vendor ~/.ai/vendor/superpowers 7.0.2 остаётся как неактивный источник для сравнения и отката. Удалять его и резервные копии не нужно.
- Сейчас omp получает 14 официальных skills через общие пользовательские ссылки. receiving-code-review разрешается единственным экземпляром из @omp-utils/code-review.
- Модели оператора: modelRoles.default = openai-codex/gpt-6.1-sol; дополнительных моделей аудит не предоставил. Не добавлять произвольные модели или провайдеры.
- task.eager=preferred; task.isolation.enabled=false; task.perCallModel=off; task.structured=false.
- Повторная проверка перед согласованием: установленный executable omp/18.20.2. PONYTAIL_DEFAULT_MODE и XDG_CONFIG_HOME не заданы, ~/.config/ponytail/config.json отсутствует; существующий эффективный default Ponytail — full.

## Рассмотренные подходы

1. Только пропатчить официальный Superpowers. Сохраняет исходный процесс, но требует самостоятельно повторить уже существующую адаптацию dispatch/model/bootstrap/workspaces. Отклонён пользователем в пользу готового форка.
2. Использовать LoneExile напрямую. Минимум собственного сопровождения, но нет владения локальным правилом Ponytail и исключением receiving-code-review. Не выбран.
3. Личный форк от закреплённого LoneExile с небольшим явно описанным diff. Выбран пользователем. Ручные обновления возможны, автоматического слежения за upstream нет.

## Границы

Входит:
- личная идентичность пакета и GitHub provenance;
- существующие 14 skills и пять sdd-* ролей исходного форка;
- перенос правила сохранения SDD при совместном применении Ponytail в задания ролей и контроллера;
- полное удаление skills/receiving-code-review из личного форка по явному решению пользователя; официальный vendor и самостоятельный @omp-utils/code-review не изменяются;
- совместимость структурированных ревьюеров с установленным omp;
- воспроизводимая установка личного пакета и штатного Ponytail для omp, отключение старых ссылок, проверка discovery, изолированный smoke fix-loop и откат.

Не входит:
- повторное подключение официального плагина в Codex или изменение его конфигурации;
- изменение ~/projects/omp-utils, его receiving-code-review и @omp-utils/code-review;
- переписывание всего Superpowers или перенос hooks и CLI Ponytail: использовать уже существующий нативный omp/Pi-плагин Ponytail.
- обход системных правил omp skill-инструкциями;
- изменения памяти, чужих skills, лишних маршрутов моделей, TTSR, разрешений инструментов или native task isolation;
- публикация в npm.

## Пакет и установка

Имя личного пакета: @yarikmix/omp-superpowers. Версия отражает исходную и локальную итерацию; документировать точный base SHA, MIT-атрибуцию и локальный diff. Сохранить upstream remote на LoneExile и происхождение obra.

omp сканирует обычную директорию skills независимо от pi.skills: одной настройки списка экспорта недостаточно. По решению пользователя удаляем skills/receiving-code-review из самого личного форка. Остальные 14 полных skill-директорий, пять agents, extension, native manifest, лицензии и provenance остаются в стандартной структуре репозитория. Bootstrap явно указывает владельца receiving-code-review — @omp-utils/code-review, без fallback в исходники.

Устанавливаем main личного GitHub-форка по точному commit: github:YarikMix/omp-superpowers#<полный-SHA>. SOURCE.md содержит upstream base SHA и описание локальных изменений. Отдельные сборка runtime-дерева и ветка dist не нужны. Не редактировать установленный кэш руками, в npm не публиковать. Официальный ~/.ai/vendor/superpowers сохраняется целиком, включая его receiving-code-review, но к omp не подключается.

До изменения global discovery получить резервную запись каждого затрагиваемого symlink: полный путь, тип, исходный target и разрешённый target. Не удалять реальные каталоги под видом ссылок, не трогать ссылки на чужие источники. Перемещать только ссылки, разрешающиеся внутрь официального vendor, в backup вне всех каталогов skills. Если фактический источник отличается от ожидаемого, остановить именно cutover и разобраться, не стирать данные.

Переключение выполняется после успешной отдельной проверки пакета. Окончательный каталог должен содержать по одному bare skill имени из личного пакета, без официальных alias-вариантов; receiving-code-review — исключительно @omp-utils/code-review. Удаление ссылок не означает удаление vendor.

## Ponytail и SDD

Базовый абзац сохраняется дословно:

> При работе по Superpowers SDD сохраняй обязательные этапы, артефакты, согласования, тестирование и ревью. Ponytail применяй для выбора простейшей реализации, полностью выполняющей согласованную спецификацию. Упрощение не должно сокращать требования или обходить этапы SDD.

В SDD-контроллере и заданиях исполнителя, task-reviewer, rereviewer, escalation-implementer и final-reviewer правило включается как часть контракта, вместе с путями спецификации и плана. Это относится к начальным dispatch и продолжению того же исполнителя. Проверки соответствуют согласованному процессу форка, не возвращают обязательное task-review каждой задачи и не добавляют отдельный Ponytail-review.

Ponytail уже имеет нативное omp/Pi-расширение. Устанавливаем его штатный пакет @dietrichgebert/ponytail 5.3.3 из GitHub по release commit 7801d061243d7b753bad0e0b3c057cd250b11755, совпадающему с тегом v5.3.3 и npm gitHead, без копирования или переписывания его ruleset. Локальная интеграция в личном форке задаёт только сохранение SDD и приоритет role-specific output contract перед общей финальной фразой Ponytail.

Сохраняем штатные режимы Ponytail и управление ими; исходный default full — явно выбранная исполнителем начальная политика для этой установки. Не менять общую конфигурацию Ponytail, если там уже задан режим: сначала прочитать применимый эффективный режим, сохранить его и проверить ожидаемое поведение. Сохраняем нативную семантику режимов по сессиям: переключение /ponytail off в родительской сессии не обещает отключения в новом worker, который самостоятельно читает общий default. Это явно документируем; механизм наследования режима не добавляем. Off отключает Ponytail в той сессии, где применён; правило сохранения SDD не включает его заново. Предложение для согласования, не утверждение о ранее выбранном пользователем always-on.

Приёмка проверяет фактическую загрузку native extension на установленном omp, его режим и взаимодействие с повторным bootstrap Superpowers. Для субагентов обязательные ограничения, spec/plan paths и точный абзац передаются в заданиях; не считать main-only injection доказательством покрытия workers. Нативный Ponytail добавляет собственные skills отдельно: число 14 относится только к нашему Superpowers-пакету.

При достижении третьего раунда реальное невыполнение согласованного требования или обязательной проверки не переводится в complete через parking. Остановить задачу как непринятую, не добавлять четвёртый раунд и не сокращать scope. Сомнительные и необязательные замечания остаются предметом штатного adjudication. Дополнительный Ponytail-review не вводится.

Глобальную запись не удалять автоматически: она используется другими клиентами и ранее не была разрешена к удалению. Для omp новые задания не должны от неё зависеть; документировать новый источник и не поддерживать два разных текста.

## Исправления совместимости omp

- У sdd-reviewer и sdd-rereviewer явно объявить structured:true рядом с output schema. Не менять глобальный task.structured только ради двух ролей; обычные исполнители продолжают возвращать текстовые отчёты.
- Уточнить mapping model: обычный per-call model запрещён текущей настройкой, но этот форк маршрутизирует модели по именованным ролям. Удалить категорическое утверждение, будто API omp никогда не имеет поля model; не требовать task.perCallModel=on.
- Проверки исполнителя явно перечислять в assignment, используя существующее системное исключение omp «unless your assignment says to». Не обещать, что skill отменяет более приоритетные инструкции; оставшееся противоречие описания task отметить в документации.
- Сохранить task.eager=preferred, task.autoParallel=off, task.isolation.enabled=false, batch=true, steps=false. Parallel waves используют механизм worktrees исходного форка, не native task isolation.

## Настройки моделей

Для локальной установки все пять sdd-* ролей маршрутизировать через operator-owned task.agentModelOverrides на уже выбранную оператором модель openai-codex/gpt-6.1-sol, с различными допустимыми reasoning levels по роли. Это предложение исполнителя для минимального изменения биллинга; не активировать Anthropic только потому, что он указан в исходном форке.

Каталог установленного omp подтверждает для openai-codex/gpt-6.1-sol уровни low, medium, high, xhigh, max. Предлагаемые локальные overrides: implementer medium; task reviewer high; rereviewer low; escalation и final reviewer max. При одном model ID escalation означает повышение effort и свежий контекст, а не более сильную другую модель. Не полагаться на молчаливое clamping.

Изменения global config показываются и подтверждаются штатным cfg approval. Включение badge фактически выбранной модели — отдельная небольшая настройка для наблюдаемости. LSP включать только при наличии относящегося к smoke/project language server; не делать его условием работоспособности всех skills.

## Проверки

1. Узкие проверки изменённых extension/agent/package контрактов. Не создавать тесты только на совпадение произвольного текста; проверки должны ловить потерю receiving exclusion, обязательного контракта worker, schema result и реального bootstrap.
2. Проверка упакованного plugin и штатного Ponytail в отдельной временной конфигурации omp: один Superpowers bootstrap, 14 Superpowers skills, пять sdd-* ролей, исключение receiving-code-review, корректные scripts paths, реальное structured yield двух review-ролей и работа режимов Ponytail. Никакого внешнего API mutation в smoke.
3. Реальный небольшой repo в отдельной временной рабочей копии: bounded implementation с явной spec/plan и covering check. Отдельный sdd-reviewer получает настоящие brief/report/diff без подсказки требуемого verdict. Если первое ревью выявит реальный дефект, используем его; если оно чистое, для детерминированного покрытия исправления в тестовый fixture прозрачно вносим содержательный дефект (убираем обязательную проверку входа), фиксируем отдельным коммитом и передаём реальный диапазон на ревью. Инъекция явно помечена в отчёте как тестовая и не приписывается исполнителю.
4. Настоящий finding передаётся через write agent://<исходный-id> тому же исполнителю, с точным абзацем Ponytail/SDD, spec/plan paths и покрывающей командой. Исполнитель исправляет реальный файл, выполняет проверку и дополняет отчёт. Настоящий sdd-rereviewer проверяет fix range. Доказательства: actual dispatch, прежний agent ID и история, diff, команды и результаты, structured verdict. Не подменять reviewer фиктивным ответом и не считать одно самоутверждение агента доказательством.
5. После cutover выполнить omp skill list --json из обычного cwd: ровно один receiving-code-review из @omp-utils/code-review без upstream aliases; остальные 14 skills из личного пакета, не из vendor. Проверить активный roster sdd-* и реально разрешённые модели.
6. Перечитать и сверить хеши защищённых файлов receiving-code-review, global памяти Ponytail и Codex config. Проверить, что посторонние изменения/skills сохранились.

## Откат

Сохранить до cutover значения только меняемых config keys и архив ссылок. При неуспешном bootstrap/discovery/smoke не оставлять частично подключённые пакеты: штатно удалить/отключить только новые личный Superpowers и Ponytail (если отсутствовал до начала), восстановить только свои ранее сохранённые ссылки и значения ключей без перезаписи всей конфигурации. Не устанавливать заново Codex и не изменять standalone receiving. Сохранить исходную package/lock-конфигурацию и учесть возможные параллельные изменения, не откатывая их целиком.

Исходники личного форка, коммиты и отчёты сохраняются для диагностики; временные smoke repos удаляются после фиксации evidence. Отчёт указывает точные команды, commit, источники skills, результат real fix-loop, оставшиеся ограничения и необходимость новой omp-сессии для plugin bootstrap.

## Что оставлено исполнителю

Раскладка install-smoke конфигурации, минимальные изменения существующих тестов и команда сбора доказательств. Подтвердить фактически установленную версию omp непосредственно перед smoke: на диске она могла обновиться независимо от текущего процесса. Не считать одни и те же названия настроек доказательством поведения между версиями. Если native Ponytail не работает на этой версии, остановить переключение и вернуться к дизайну; не писать неоговорённый replacement.

После согласования: implementation plan, затем выполнение четырёх согласованных пользовательских этапов без промежуточных запросов о продолжении; внешние публикации/применение настроек подчиняются штатным разрешениям.

После этого пользователь отдельно согласовал удаление receiving-code-review непосредственно из личного форка вместо сложной упаковки и ветки dist. Итоговый упрощённый дизайн согласован через форму decision=approve. Остальные ограничения и приёмка сохранены.
